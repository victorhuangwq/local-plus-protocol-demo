Should websites be able to open your app?

Use local+ for app entry points that other native apps need to call, but websites should not launch.

Your Windows or macOS app may already handle custom URLs such as myapp:hello. In supporting browsers with the feature enabled, registering a scheme beginning with local+ blocks web-initiated launches of that scheme. Native apps can still call it through the OS.

What changes for your app

Ordinary and local-only entry points
What you doOrdinaryLocal-only
Register a schememyapp:local+myapp:
Open a URL from another native app through the OSmyapp:hellolocal+myapp:hello
Open a website link in a supporting browser with the feature enabledNormal app-opening flowBlocked

Windows: register local+myapp using your usual protocol-registration mechanism. macOS: declare local+myapp in your app's URL schemes. Registration uses the scheme name without the trailing colon.

Update callers to open the full URL, such as local+myapp:hello, and make sure your handler accepts the new scheme. The OS dispatches that URL to your app as usual.

This is a new protocol name, not a setting on the old one. There is no automatic mapping from myapp: to local+myapp:. Keeping the old scheme wired to the same functionality leaves that entry point reachable from websites.

Keep validating incoming URLs. This is a browser restriction, not authentication or OS-level protection. Unsupported browsers may not enforce it, and administrator policies can override it.

See the browser block, no app installation needed

The links below use toydemo: and local+toydemo:. No demo app is installed: compare a request that reaches app lookup with one the browser rejects before lookup.

Set up your test browser

Use the latest Chrome Canary or Edge Canary. Fully quit that browser, including any background processes, before running one command below. Then open this page in the new window. These commands use your normal Canary profile, including its existing settings and sign-ins.

Windows (PowerShell)

Chrome Canary:

& "$env:LOCALAPPDATA\Google\Chrome SxS\Application\chrome.exe" --enable-features=LocalOnlyAppProtocolPrefix

Edge Canary:

& "$env:LOCALAPPDATA\Microsoft\Edge SxS\Application\msedge.exe" --enable-features=LocalOnlyAppProtocolPrefix

macOS (Terminal)

Chrome Canary:

open -a "Google Chrome Canary" --args --enable-features=LocalOnlyAppProtocolPrefix

Edge Canary:

open -a "Microsoft Edge Canary" --args --enable-features=LocalOnlyAppProtocolPrefix

These commands use standard Canary installation locations. Nothing else is installed. This page cannot enable or detect the feature.

  1. Enable the feature using Set up your test browser above.
  2. Open DevTools with F12 or Ctrl+Shift+J on Windows, or Command+Option+J on macOS. Select Console and make sure Info and Error messages are visible.
  3. Click each link below separately. Compare the browser's console messages. The page may look unchanged; the console is the evidence.

Ordinary protocol

toydemo:hello

Try ordinary protocol

Expected: the browser looks for an installed app. This demo hasn't installed one, so on Windows and macOS the console reports that the scheme has no registered handler.

Local-only protocol

local+toydemo:hello

Try local-only protocol

Expected with the feature enabled: the browser refuses the website's request before looking for an app. The console reports:

Not allowed to launch 'local+toydemo:hello'.

Each click logs the requested protocol. This is a page-generated message, not confirmation that the browser searched for or found an app. Even a deliberate click on a webpage is web-initiated.

These are expected outcomes, not live status indicators. A webpage cannot reliably tell whether an external app launched or read these browser-generated console messages.

No app is supplied or installed. If you already have an app registered for either demo scheme, the ordinary launch flow may offer to open it; cancel that prompt if you do not want to open the app.

If both links behave the same

Update Chrome Canary or Edge Canary, fully quit it, and relaunch with --enable-features=LocalOnlyAppProtocolPrefix. An older browser can accept an unknown feature flag without implementing it. Enterprise policies can also affect the result.

As a control, fully quit the same compatible browser and relaunch with --disable-features=LocalOnlyAppProtocolPrefix. Both links should then follow normal handler lookup, assuming no overriding policies or other restrictions.

What this does not demonstrate

This demonstrates rejection, not successful app launching. Typing a local-only URL directly into the address bar retains the normal launch flow, but opening an app still requires a registered handler.

This is browser enforcement, not OS access control. Administrator policies AutoLaunchProtocolsFromOrigins and applicable URLAllowlist settings can override the block; remembered user allowances cannot. Other browsers or builds may behave differently.
